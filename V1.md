# V1 — Building now

Scope locked 2026-08-11. Anything not in this file is [LATER.md](LATER.md). Decisions, costs and design rationale live in [PROJECT.md](PROJECT.md).

**The shape of v1:** a landing page that captures leads, a CRM where the front desk works those leads into members, and a member portal that shows people what they bought. Money is handled in person — no checkout, no gateway.

**Where it all lives:** a pnpm workspace with three packages.

```
apps/web       landing page + member portal + CRM   → maxfitbangalore.in (Vercel)
apps/backend   DB schema + API (edge functions)     → Supabase
apps/trigger   scheduled jobs                       → Trigger.dev
```

Everything user-facing ships from one domain out of a single Vercel deploy — portal and CRM as lazy-loaded routes so none of that code reaches a visitor who only sees the homepage. The API is Supabase Edge Functions in `apps/backend`, deployed separately, on Deno rather than the app's Node dependencies ([comparison](PROJECT.md#vercel-functions-vs-supabase-edge-functions)). Individual endpoints can move to Vercel Functions where that fits better. Deliberately provisional: this is the build-and-test setup, and pieces move later if they need to.

## 1. Landing page

Mostly built (`apps/web/`). Remaining work is the lead path, not the design.

- [x] Wire the free-trial form to the `leads` table — inserted straight from the browser with the Supabase client, no edge function in between ([why](#leads-without-an-endpoint))
- [x] On success → redirect to `/trial-claimed`
- [ ] Swap placeholder content: real photos, real equipment list, empty out `reviews` + `transformations` until real ones exist

Content blockers are tracked in PROJECT.md → Open Questions. **The hero promises a callback "within a few minutes"** — that commits someone to answering the phone during opening hours. Confirm before launch or soften the copy.

## 2. Trial-claimed page — `/trial-claimed` ✅ built

Exists for one reason: **Google Ads needs a destination URL to count a lead conversion.**

- [x] Real route, not a modal or an in-place state swap — Ads fires on pageview, so it must be a navigation
- [x] `noindex` — it should never show up in search results
- [x] "Free trial claimed — walk in any time during opening hours", with hours, address, call + WhatsApp CTAs
- [x] Insert the lead, then redirect here on submit success
- [x] **Gated on a session flag** — a direct visit bounces to `/`, so Ads can't count a bookmark or a shared link as a second lead
- [x] Map, copy-address button and Save in Maps, so the visitor can actually find the place
- [ ] Fire a PostHog event on mount, so both analytics stacks agree on the number

The gate is two flags, not one (`apps/web/src/lib/trialClaim.ts`): *may they see the page* lasts the session, so a refresh to re-read the address still works; *should the conversion fire* is a one-shot token, so a refresh doesn't count twice.

### Leads without an endpoint

The `leads` edge function isn't being built. The browser inserts into the table with the publishable key and RLS does the fencing: a **column-level grant** lets anonymous callers write `name`, `phone`, `email` and `source` only, and the insert policy pins `source` to `free_trial` — so nobody can self-serve a `converted` status or attach themselves to a member. There's no select policy for `anon` at all, so the lead list can't be read back.

The one thing an endpoint would have bought is abuse control. Nothing rate-limits this today; if it gets hit, the fix is Turnstile in front of the insert, or moving it behind the function after all.

## 3. User accounts

**OTP is the whole auth story — no passwords.** Phone number in, six digits back, delivered over WhatsApp. Signup, login and phone verification are all the same primitive.

- [ ] Create account from the UI (phone + name; email optional, for receipts and recovery)
- [ ] Login — `signInWithOtp({ phone })` → `verifyOtp(...)`, no password anywhere
- [ ] Verify a phone on an existing account (`updateUser({ phone })` → `verifyOtp({ type: 'phone_change' })`) — same flow, used when the desk attaches a login to a walk-in member
- [ ] Basic role separation: `member` vs `staff`/`owner` — needed for the admin panel to exist at all

**We build delivery, not OTP.** Supabase Auth's **Send SMS hook** points at an edge function in `apps/backend`; Auth generates, stores, rate-limits and verifies the code, and hands it to us to deliver. Whether it goes out over WhatsApp Cloud API, SMS, or email fallback is a detail inside that one function — Auth and the client neither know nor care. Mechanics and gotchas (signature verification, rate limits, the synchronous response) in [PROJECT.md](PROJECT.md#how-its-wired--supabase-send-sms-hook).

**Ship on email OTP, flip to WhatsApp later.** Meta business verification takes weeks and the site ships before it clears. Because the channel lives behind the hook, flipping is one function plus a dashboard toggle — nothing in the app changes, and there's no untested branch waiting to surprise us.

## 4. Member portal — subscription

What a logged-in member sees about the plan they bought:

- [ ] Plan name and price
- [ ] Purchase date
- [ ] End date
- [ ] Pause days: total allowance, used, remaining
- [ ] **Pause action** — pause for a day or more, drawing down the allowance

Freeze policy is already confirmed: **15 days a year for annual members.** That's the allowance.

**Two design points that will bite if got wrong:**

- **Derive the end date, never store it as a fixed value.** `end_date = purchase_date + plan_duration + pause_days_consumed`. A pause extends expiry, so a stored end date drifts out of sync the first time anyone pauses, and every downstream thing — the expiry worker, the dashboard counts, the members filter — reads that same wrong date.
- **Pause is a date range, not a counter.** The dashboard needs "who is paused *today*", which a running total can't answer. Store `pause_periods` rows (`start_date`, `end_date`) and compute both the consumed count and today's paused set from them.

**Needs a decision before building** (see Open Questions below): can members pause themselves, or does staff approve it?

## 5. Expiry reminder worker

- [ ] Runs daily
- [ ] Finds plans expiring within 3 days
- [ ] Sends a WhatsApp notification

**Where it runs: Trigger.dev.** Vercel Cron was ruled out — Hobby is daily-only, UTC-only, and fires anywhere within the scheduled hour, which is three problems for an IST-sensitive reminder. Trigger.dev's free tier gives 10 schedules and no task timeout; v1 needs one. The job queries Postgres daily, so it also doubles as the keep-alive that stops the **Supabase free tier pausing after 7 days inactivity** — make sure it still hits the DB on days it finds nobody to remind, or the keep-alive silently stops working exactly when the gym is quiet.

**Must-haves:**
- **Idempotency.** A retry, a double-run, or a redeploy must not send the same member two reminders. Log sends (`reminder_sent_at` on the plan, or a `notifications_sent` table keyed by plan + type) and check before sending. Trigger.dev's free tier keeps only **1 day of logs**, so this table is also the only durable record of what actually went out.
- **IST timezone.** "Expiring in 3 days" computed in UTC is off by a day for evening expiries.
- **This is a utility template, not authentication** — separate Meta template, separate approval, same ₹0.115 rate.

⚠️ **Critical path:** this and the OTP both depend on the same verified WABA. Meta business verification gates *both* v1 WhatsApp features, and it needs PAN/GST/live website (+CIN if Pvt Ltd). Start the paperwork now — it's the longest lead time in v1 and no code unblocks it.

## 7. Analytics — PostHog

- [ ] Session recording on the landing page
- [ ] CTA click events

**Instrument these CTAs:** Call now (nav + sticky mobile bar), Free trial (hero + sticky bar), Chat on WhatsApp (red band), plan card buttons, form submit, thank-you page view. Name them consistently from the start — renaming events later orphans the history.

⚠️ **Mask form inputs in session recordings.** They capture keystrokes by default, and the lead form collects a name and phone number. PostHog masks inputs by default but verify it, especially on the phone field.

# Last in the order

In v1, but built after everything above. Both were nearly deferred; they're in because they're cheap once the rest exists, not because they're urgent.

## 8. Invoices

- [ ] Generate a PDF per payment, upload to Cloudinary, store the URL on the payment row
- [ ] Member portal: payment history with invoice downloads

Server-side generation in a Vercel Function using **pdfkit**. Puppeteer is off the table here — Chromium breaks both the 250 MB bundle limit and the 10s Hobby duration cap. If HTML templating proves worth it, run generation as a Trigger.dev task instead, where neither limit applies.

⚠️ **The GST answer has to land before the schema is written, not before this feature is built.** If the gym is GST-registered, invoices need GSTIN, HSN/SAC and a tax split. Retrofitting tax fields onto payment rows that already have production data is materially worse than leaving room for them now. This is the one part of a last-in-the-order feature that isn't safe to defer.

## 9. PWA / offline shell

- [ ] Installable on phone
- [ ] Offline shell

**Self-host the fonts first.** They currently load from the Google Fonts CDN, so the shell isn't genuinely offline until that changes — and swapping font delivery after the fact means re-testing the display type, which is load-bearing for the whole design.

## Open questions blocking v1

1. 🚩 **Is the gym GST-registered, and is it Pvt Ltd or proprietorship?** Gates Meta business verification, which gates both WhatsApp features. Longest lead time in v1 — needed from Max first.
2. 🚩 **Is `+91 831 089 0652` already on WhatsApp or WhatsApp Business?** A WABA number can't already be on WhatsApp; registering it destroys that account's history. May need a second SIM.
3. **Can members pause their own plan, or does staff approve?** Self-serve is friendlier but abusable — though the 15-day cap already limits the damage. Changes both the UI and the permissions model.
4. **What does staff do when a member has no WhatsApp or the OTP doesn't arrive?** Email fallback exists, but the desk needs a defined path, not an improvised one mid-sale.
5. **The hero form's callback promise** — "within a few minutes" commits someone to answering the phone during opening hours. The `/trial-claimed` page now says *walk in any time* instead, which is a weaker promise and easier to keep. Worth aligning the hero copy to match.
