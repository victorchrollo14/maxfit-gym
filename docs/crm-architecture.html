MaxFit CRM: how members, memberships, money and pauses work

How the front desk adds a member, sells a membership, records payments and pauses a yearly plan. Each flow is checked against the current Supabase schema, and every gap is marked.

Updated 4 Oct 2026Scope architecture only. Implementation steps come after sign-off.Source apps/backend/supabase/migrations as of 34d728a

02Ground rules

Every flow below follows these.

Every member can log in

A member is a Supabase auth user with a phone number. Phone sign-up is off ([auth.sms] enable_signup = false), so the CRM is the only way a member account gets created, and the portal's phone-OTP login works from day one.

Balances are never stored

Amount paid and amount pending are always summed from payments. There's no balance column that can drift from the actual payments.

end_date is the real expiry

It always holds the day the membership actually ends, pauses included. A trigger on pause_days recalculates it as start_date + duration_days − 1 + days paused, so it can't drift from the pauses. The original end can always be recalculated from the start date and duration.

"Today" means today in IST

Timestamps (created_at, paid_at) are timestamptz, stored as UTC and shown in IST. Membership and pause dates are plain dates: calendar days with no time or zone, inclusive on both ends. The rule is about comparing them to today, which always has to be the IST day.

Why "today" has to be the IST day

Between 00:00 and 05:30 IST, UTC is still on the previous day. The EC2 server runs in UTC, so new Date().toISOString().slice(0, 10) on 4 Oct at 1 AM IST gives 2026-10-03. A membership ending 3 Oct would still look active, and a pause "from tomorrow" would start a day early. So:

  • SQL: always today_ist(), never current_date or now()::date.
  • TypeScript: one helper, todayIST(), using Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Kolkata' }). Never take the date from new Date() directly.
  • Date pickers send YYYY-MM-DD strings, never Date objects, which carry a timezone with them.

D1 Agreed 4 Oct

No membership or pause functions. Server functions check the rules and do the writes. The database keeps its constraints (pause no-overlap, discount checks) and the triggers that keep end_date in sync with the start date, duration and pauses.

Accepted trade-offs. A membership and its seats are two inserts, so the server function deletes the membership if the seats fail. Two pauses saved at the same instant could both pass the allowance check, which a single front desk won't hit.

D18 Agreed 6 Oct

The rule is per table, not per action: memberships, seats, pauses and payments are written only by server functions, and the browser keeps read-only RLS on them. Every server function goes through one requireAdmin middleware: the browser sends its access token, the server verifies it with getClaims and checks app_metadata.admin (the same claim RLS reads), then writes with the service-role key.

On screen

Both ways in open the same Add member drawer: the button on the Members page, and Convert to member in a lead's drawer.

The drawer

  • Name and phone (+91 prefix), with email, gender, date of birth and notes under a collapsed "More details"
  • A banner as soon as the number is valid (Step 1 below)
  • "Verify phone": Send WhatsApp code (send, 6-digit box, check, resend timer) or I've verified this number
  • Create member works once the code checks out or the second option is picked
  • Then the member page opens with the New membership form already up. The admin closes it if they're only adding a login.

From a lead

  • One button, Convert to member, in the existing lead drawer
  • Opens the drawer with name, phone, email and notes copied from the lead. Phone stays editable in case the lead has a typo.
  • After saving, the drawer shows the converted chip and Open member page. The card moves to the Converted column, and status stays locked as today.

Step 1: is this person already here?

As soon as a valid number is typed, the CRM looks it up:

  • Already a member: a red banner links to their member page, and Create member is blocked. auth.users.phone is unique, so a duplicate would fail anyway, but showing the existing member is friendlier. When the drawer was opened from a lead, it offers "Link lead to Priya Raman" instead, which marks the lead converted against that member without creating anyone.
  • An open lead (when opened from the Members page): a yellow banner says the lead will be marked converted. Saving sets leads.user_id, status = 'converted' and converted_at. The table's check constraint already pairs those last two.
  • Nobody: carry on.

Step 2a: verify by WhatsApp code

Supabase's own phone OTP does the work, called from the server. From the admin's browser, verifyOtp would sign the browser in as the member and replace the admin's session. On the server, the member's session is created and thrown away, and the admin's session is never touched. The existing send-wa-otp hook delivers the code on WhatsApp.

Step 2b: verify by admin

The admin has already spoken to the person on that number, or the person is standing at the desk. They pick "I've verified this number" and the server creates the user with phone_confirm: true. We don't record which of the two was used.

D9 Agreed 4 Oct

Two ways to verify: WhatsApp code or the admin's "I've verified this number". No "Verify later". Remote sales use the second, since the admin has just spoken to them on that number.

D8 Agreed 4 Oct

Keep the phone copy in user_profiles, since the browser can't read auth.users. handle_new_user and handle_user_updated add the + when GoTrue has stripped it, so user_profiles.phone and leads.phone are both E.164 and lookups by number match.

04Member photos

So the front desk can match a face to a name. Stored on Cloudinary, private.

  • Capture: <input type="file" accept="image/*" capture="user"> opens the camera on a phone or tablet at the desk and the file picker on a laptop.
  • Size: resized in the browser before upload, so each photo is about 100–150 KB. Two thousand members is roughly 300 MB, well inside the free tier. This is the only change made before upload.
  • Naming: the Cloudinary public_id (its name for the file's path, nothing to do with visibility) is profile/<user_profiles.id>. One photo per member, and a new upload overwrites it. We store v<version>/profile/<id>, so a new photo busts the cache. There's no orphan cleanup to do.
  • Two sizes, made on request: the original is stored once, and the size lives in the URL. There are only two, the same on desktop and mobile, defined once in code:
    • avatar: c_fill,g_face,w_160,h_160,f_auto,q_auto, a square face crop shown at 80px (160px keeps it sharp on high-density screens)
    • full: c_limit,w_800,f_auto,q_auto, the whole photo, for the member page and a tap-to-enlarge view
    Cloudinary makes each the first time it's asked for and caches it. Nothing is pre-generated at upload, and the server signs only these two.
  • Private: uploaded as type authenticated, so Cloudinary serves an image only from a URL our server has signed. The signature covers the size too, so the browser can't ask for the full-size original or any size the server didn't sign. When a list loads, one server call signs that page's URLs.
D10 Agreed 4 Oct

Photos are private (authenticated type, server-signed URLs), stored as profile/<user_profiles.id>, in two sizes only: avatar (160px face crop) and full (800px).

Limit: signed URLs don't expire

A standard signed Cloudinary URL works for as long as the photo exists, so a leaked link stays open. The protection is that nobody can build or guess a working link, or ask for other sizes. Links that expire need Cloudinary's token-based access, a paid feature, or serving photos through our own server. Uploading a new photo creates a new version, but the old file can stay in Cloudinary's cache until it's purged, so it isn't a reliable way to kill a link.

05Creating a membership

From the member page: "New membership", which also handles renewals.

On screen

"New membership" on the member page (and "Renew" on the current card) opens one drawer. The steps sit in order in one scroll, not a wizard, and a summary updates as you go.

  • Plan: cards from src/plans.ts. Picking a 2-seat plan adds a Second member field with name or last-4-digits search. Its "New" button opens the Add member drawer on top and returns here with that person filled in.
  • Start date: today, or the day after the current membership ends. The summary shows the end date it works out.
  • Discount: amount and reason. Offers we run show as chips that fill both in (e.g. "Festival offer −₹1,000" on Annual). No reason, no save.
  • Summary: price, discount, amount due, dates and pause days.
  • Payment: "Record a payment now" is ticked, with the amount due filled in. Lower it for a part payment. UPI and card need a reference, and cash doesn't. Untick it and the full amount goes to Has dues.
  • Create membership: the server function writes the membership, its seats and the payment, and the card appears on the member page.
  • Renew opens the same drawer with the current plan picked, once the current membership has ended (D17).
D13 Agreed 4 Oct

New membership and Renew share one drawer: plan, second member if needed, start date, discount with reason, live summary, optional payment.

Start date

  • No current membership: defaults to today.
  • Renewal: only once the current membership has ended (D17), so it defaults to today like any new sale.
  • The admin can move it forward, for example "start Monday". duration_days is copied from the plan, and end_date = start_date + duration_days − 1 until a pause pushes it out.
  • Rule: one person can't have two memberships covering the same day. Checked across every seat, so both partners on a Couple Pass are free.

Where plans live

There's no plans table. The catalogue is a typed list in code, src/plans.ts, used only by the CRM. The landing page keeps its own list in content.ts, and the two are not kept in sync: the site can show festival prices and other offers as often as marketing wants, and the CRM sells the regular plan with a discount and a reason. Adding a plan, changing a price or taking a plan off sale in the CRM is a code change and a deploy.

Plan vs membership: which one is true?

Both, for different questions. The plan is read once, when the membership is created. Its terms are copied onto the membership. After that, nothing reads the code list to answer a question about that membership.

PlanMembership
What it isThe list in code: what we sell todayThe deal: what this person bought
Answers"What does an Annual Pass cost right now?""What did Priya pay, how many pause days does she have, when does she expire?"
ReadOnce, to fill the new-membership formEvery time after that
Copied across at saleplan_key, plan_name, price, duration_days, pause_days_allowed

The membership shows its own plan_name, so renaming or removing a plan in code never changes history. plan_key is for reports ("Annual Passes sold this month") and for defaulting a renewal to the same plan. Seats aren't copied: they're checked at sale, and the seat rows already record who's on the membership.

The price comes from the server

The browser sends the plan key, start date, seat holders, discount and reason, and never a price. The server function looks the plan up in src/plans.ts, checks the seat count and inserts the membership and its seats with the service-role key. Browser roles have no insert on memberships or membership_users, so no membership can be written with terms the code doesn't have. With no foreign key, this is also what keeps plan_key valid.

Changing prices and running offers

  • Price change: edit the price in src/plans.ts and deploy. Memberships already sold keep their copied price. Price history is the memberships grouped by plan_key and price, plus the git history of the file.
  • Offers are never a separate plan or a price edit. They're sold as the normal plan with a discount and a reason, e.g. Annual Pass ₹9,999 − ₹1,000 "Festival offer". An offer we run often can be listed in code so the form pre-fills the amount and reason. A one-off deal is typed in by the admin.
  • Taking a plan off sale: set onSale: false. It disappears from the picker, and existing memberships are untouched.
  • Renewals default to the same plan_key at today's price. If that plan is off sale, the admin picks another. Loyalty pricing goes in as a discount.

Price and discount

price is copied from the code list as is and can't be edited in the form. A different price is entered as a discount with a reason (e.g. "Festival offer", "Referral from Arjun"). amount_due = price − discount_amount. Checks keep the discount between 0 and the price, and require a reason whenever it's above 0. This way price always means "list price on the day it was sold", every difference has a stated reason, and total discount given can be reported, by offer.

Durations are in days: 30 / 90 / 180 / 365. A membership can start on any day, and end_date = start_date + duration_days − 1. A Monthly Pass from 17 Oct runs to 15 Nov, and pauses add whole days on top.

Status lifecycle

Status is never stored. It's computed from dates, pauses and cancellation by one view (see 09). Payment status is a separate field shown next to it.

Couple Pass

  • One membership, two membership_users rows. seats: 2 in the code list caps it, checked by the server at sale.
  • Payments attach to the membership. paid_by records whichever partner paid each instalment.
  • Pauses attach to the membership, so both partners pause together (D16).

Renewing

Renewals aren't queued ahead of time. When a member's current membership ends, the admin clicks Renew and sells the next one, starting that day. A member who pays for the renewal while the current plan is still running gets a note on their page for now; the membership is created when the current one expires. How an advance payment is recorded is decided later.

D17 Agreed 6 Oct

No queued renewals. The new membership is created once the current one ends, so nothing has to move when a pause pushes an end date out. Early renewal payments are a note for now.

D12 Agreed 4 Oct

No mid-way plan changes in the CRM. If someone really must switch now (e.g. to a Couple Pass), the admin does it by hand: cancels the current membership, works out the credit themselves, and enters it as the discount on the new one with a reason. The CRM does no credit maths. The cancel drawer only shows the days left on the membership, as information.

  • Wrong entry: payments are never edited or deleted. The admin voids one with a reason and enters it again. Proposal: add 'void' to the status check, plus void_reason.

07Pausing a membership

The member calls, the admin pauses it in the CRM. Only memberships with pause_days_allowed > 0, copied from the plan at sale: 15 days on yearly plans, 7 on six-month, none on monthly or quarterly (set in src/plans.ts).

Rules

  • Dates are inclusive. Days = paused_to − paused_from + 1.
  • The pause has to start today or later, and within the membership's start_date and end_date.
  • Days used across all pauses + this one ≤ the membership's pause_days_allowed, not the plan's. Checked by the server function before the insert (D1).
  • No overlap with another pause. The existing pause_days_no_overlap constraint already enforces this.
  • Resume early: paused_to becomes yesterday and resumed_early_on today. Unused days go back to the balance.
  • Cancel a future pause: delete the row. Changing the dates of a future pause = cancel + new pause.

08What the admin sees

Two pages for members and memberships, plus the dashboard and leads. Memberships don't get a page of their own. Exact layouts come later.

Members

One row per member: photo, name, current plan and end date, status pill and dues. Search by name or the last 4 digits of a phone number. Filter chips: All, Active, Paused, Expiring, Expired, Has dues. "Add member" opens the drawer from 03.

Member page

Header with photo, name, phone and a verified chip. The current membership card shows plan, dates, days left, pause days left and paid/due, with Record payment, Pause and Renew, and Cancel under "…". Each action opens a drawer. Below it, a history of past and upcoming memberships, payments and pauses.

Dashboard

Today's numbers from the summary view: active, paused today, starting today, expiring this week, collected today by method, total pending. Membership reports ("Annual Passes sold this month") go here later.

Leads

As built, plus "Convert to member" in the drawer, which opens the Add member drawer pre-filled (03).

Why memberships live on the member page

  • Every request starts from a person ("Priya wants to pause"), so the desk finds the member and acts on their membership card.
  • The members list already shows each member's current membership, so its filters cover what a memberships list would.
  • Has dues (pending above 0, oldest first, with a WhatsApp reminder link) and Expiring (end_date in the next 7 days) are filters on the members list, not pages of their own. The Trigger.dev reminder job reads the same Expiring query.
  • A membership that starts later (e.g. "start Monday") shows as "Upcoming" above the current card.
  • A Couple Pass shows the same card on both partners' pages, and its actions work from either.
D11 Agreed 4 Oct

No separate memberships page. Memberships are created and managed from the member page. Dues and Expiring are filters on the members list.

10Also to discuss

You asked what else belongs in the architecture. These are the topics I'd add, roughly in order of how soon the desk will hit them.

Check-ins / attendance

The photo is there to know who's coming in. Do we log visits, and how: the admin taps a member, or members scan a QR at the door? A check-in during a pause or after expiry should warn the desk.

Renewal reminders

The Trigger.dev job is a placeholder. It reads end_date directly, and needs an approved WhatsApp template and a send log, so nobody gets messaged twice.

Cancellations & refunds

Who can cancel, whether money goes back, and how it shows on the books.

Staff roles decided

Only two people use the CRM for now, both with full access: admin and claims_admin (plans_admin goes with the plans table). Narrower claims for front-desk staff, e.g. no voids, cancellations or large discounts, come when someone else needs access.

Audit trail

created_by and marked_by cover creation. Edits to profiles, voids and cancellations need an activity_log if we want "who changed this?"

Member portal

What members can see once they log in: their membership, dues, receipts, pause balance, and maybe self-pause.

Reports

Collected per day by method (to match the cash drawer), monthly revenue, total pending, new vs renewals, lead conversion.

Existing members after v1

About 80–100 members bought before the CRM. They're imported once the flows below are built, with their real start dates, payments and verification. Planned then.

Other products

payments.membership_id is nullable. Is that for personal training, supplements or day passes? If yes, they need their own model.

Privacy

Photos, phone numbers and dates of birth are personal data under India's DPDP Act. Decide who can see what, how long we keep it, and what happens when a member asks to be removed.

12Build order

Each phase is usable on its own and unblocks the next. Migrations are new files only; applied ones are never edited.

Phase 1 · One migration

Applied to prod, so check whether memberships has rows first. If it does, the backfill from plans runs before the drop.

  • memberships: add plan_key, plan_name, price, duration_days, pause_days_allowed, cancelled_at, cancelled_by, cancel_reason. Discount checks (at most the price, and a reason when above 0). Backfill, then drop plan_id.
  • Drop plans, its policies and its seed rows. Remove plans_admin from CLAIMS and the seeded admin.
  • The end_date triggers: on memberships (insert, or a start or duration change) and on pause_days (a pause added, changed or removed).
  • payments: paid_at, note, void_reason, no status default, 'void' in the check.
  • The + in the auth triggers.
  • RLS: no browser writes on memberships, membership_users, pause_days or payments (D18).
  • membership_summary view (status, paid, pending, pause days used and left). The dashboard numbers read from it in code.

Phase 2 · Shared code

  • src/plans.ts, the CRM plan list.
  • todayIST() and the existing phone normaliser.
  • Cloudinary: sign an upload, and sign avatar / full URLs.

Phase 3 · Server functions

  • sendPhoneCode (creates the unconfirmed user, then Supabase signInWithOtp), checkPhoneCode (server-side verifyOtp), cancelPhoneCode (deletes the unconfirmed user)
  • createMember, which also links a lead, or links a lead to an existing member
  • createMembership: seats and an optional first payment, deleting the membership if the seats fail
  • cancelMembership
  • addPause, resumePause, cancelPause, with the allowance check
  • signAvatarUpload, signAvatarUrls
  • recordPayment, which checks the amount against what's pending, and voidPayment.

Phase 4 · Screens

  • Members list with search and filters, and the Add member drawer
  • "Convert to member" in the lead drawer
  • Member page: header, photo upload, current membership card, history
  • Drawers: New membership / Renew, Record payment, Pause, Cancel
  • Dashboard numbers from the summary view

After v1

  • Reconciliation, narrower staff claims, check-ins and reports
