MaxFit CRM: how members, memberships, money and pauses work

How the front desk adds a member, sells a membership, records payments and pauses a yearly plan. Each flow is checked against the current Supabase schema, and every gap is marked.

02Ground rules

Every flow below follows these.

Every member can log in

A member is a Supabase auth user with a phone number. Phone sign-up is off ([auth.sms] enable_signup = false), so the CRM is the only way a member account gets created, and the portal's phone-OTP login works from day one.

Balances are never stored

Amount paid and amount pending are always summed from payments. There's no balance column that can drift from the actual payments.

end_date is the real expiry

It always holds the day the membership actually ends, pauses included. A trigger on pause_days recalculates it as start_date + duration_days − 1 + days paused, so it can't drift from the pauses. The original end can always be recalculated from the start date and duration.

"Today" means today in IST

Timestamps (created_at, paid_at) are timestamptz, stored as UTC and shown in IST. Membership and pause dates are plain dates: calendar days with no time or zone, inclusive on both ends. The rule is about comparing them to today, which always has to be the IST day.

Why "today" has to be the IST day

Between 00:00 and 05:30 IST, UTC is still on the previous day. The EC2 server runs in UTC, so new Date().toISOString().slice(0, 10) on 4 Oct at 1 AM IST gives 2026-10-03. A membership ending 3 Oct would still look active, and a pause "from tomorrow" would start a day early. So:

  • SQL: always today_ist(), never current_date or now()::date.
  • TypeScript: one helper, todayIST(), using Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Kolkata' }). Never take the date from new Date() directly.
  • Date pickers send YYYY-MM-DD strings, never Date objects, which carry a timezone with them.

Where writes run

The CRM writes leads straight from the browser today, and admin-claim RLS keeps that safe. The new flows break into three kinds of write:

KindExamplesRuns in
Needs a secretCreate an auth user, send a WhatsApp code, sign a Cloudinary uploadTanStack Start server function (service-role key, WABA token, Cloudinary secret)
Several rows that must land together, or a rule that reads other rowsMembership + its seats; a pause checked against the allowance and the next membershipA Postgres function called from a server function, so it runs in one transaction

D1 Decision needed

You dropped the membership and pause RPCs on purpose. supabase-js has no transactions, so if the rules live only in TypeScript, a membership can be created without its seats, and two pauses saved at the same moment can both pass the allowance check. My recommendation: keep invariants in the database (constraints, triggers, two small functions) and do orchestration and secrets in server functions. The alternative is a direct Postgres connection from the server (postgres.js over the Supabase pooler) so the server functions can open real transactions themselves.

Step 1: is this person already here?

As soon as a valid number is typed, the CRM looks it up:

  • Already a member: stop and link to their member page. auth.users.phone is unique, so a duplicate would fail anyway, but showing the existing member is friendlier.
  • An open lead: offer "Convert this lead". Saving then sets leads.user_id, status = 'converted' and converted_at. The table's check constraint already pairs those last two.
  • Nobody: carry on.

Step 2a: verify by WhatsApp code

We can't use Supabase's own phone OTP here. signInWithOtp + verifyOtp signs the browser in as the member, which would replace the admin's session. Instead the server runs its own short-lived code using the WhatsApp template we already send:

Step 2b: verify by admin

The admin has already spoken to the person on that number, or the person is standing at the desk. They pick "I've verified this number" and the server creates the user with phone_confirm: true. It records phone_verified_via = 'admin' and phone_verified_by = <admin id>, so the audit trail shows who vouched for it.

Q1 Open question

Should there be a third option, "Verify later"? The member would be created with an unconfirmed phone and a "Phone not verified" chip. Their first portal login by phone OTP would confirm the number automatically. That helps when a membership is sold over the phone to someone who isn't at the desk.

Schema fix

Normalise the phone in handle_new_user / handle_user_updated (add the + when GoTrue strips it), so user_profiles.phone and leads.phone use the same format and lookups by number work.

04Member photos

So the front desk can match a face to a name. Stored on Cloudinary.

  • Capture: <input type="file" accept="image/*" capture="user"> opens the camera on a phone or tablet at the desk and the file picker on a laptop.
  • Size: resized in the browser before upload, so each photo is about 100–150 KB. Two thousand members is roughly 300 MB, well inside the free tier.
  • One photo per member: the public_id is fixed per member and uploads overwrite it. We store v<version>/<public_id>, so a new photo busts the cache. There's no orphan cleanup to do.
  • Display: build the URL with transforms, e.g. c_fill,g_face,w_160,h_160,f_auto,q_auto for avatars.
Q2 Open question

Public or private delivery? Member faces are personal data. With Cloudinary's authenticated type, every image URL has to be signed by our server (one batch call when a list loads). Public URLs are simpler, but anyone with the link can open them. I'd lean private.

05Creating a membership

From the member page: "New membership", which also handles renewals.

Start date

  • No current membership: defaults to today.
  • Renewal (has an active or upcoming membership): defaults to the day after its end_date, so the new one queues behind it. This is what the dropped create_membership did.
  • The admin can move it forward, for example "start Monday". duration_days is copied from the plan, and end_date = start_date + duration_days − 1 until a pause pushes it out.
  • Rule: one person can't have two memberships covering the same day. Checked across every seat, so both partners on a Couple Pass are free.

Plan vs membership: which one is true?

Both, for different questions. The plan is read once, when the membership is created. Its terms are copied onto the membership. After that, nothing reads the plan to answer a question about that membership.

PlanMembership
What it isThe catalogue: what we sell todayThe deal: what this person bought
Answers"What does an Annual Pass cost right now?""What did Priya pay, how many pause days does she have, when does she expire?"
ReadOnce, to fill the new-membership formEvery time after that
Copied across at saleprice, duration_days, pause_days_allowed

plan_id stays on the membership as a record of which product was sold. It's used for reports ("Annual Passes sold this month"), for showing the plan name, and for defaulting a renewal to the same plan. It is never used for that membership's money or dates. max_seats isn't copied, because it's only checked at sale and the seat rows already record who's on the membership.

Changing a plan's price

A plan's terms never change once it exists. A new price means a new plan row that points back to the old one. This keeps plan_id meaningful: one row is one price point, so "Annual Passes sold at ₹8,999 vs ₹9,999" is a group-by on plan_id, and the chain of rows is the pricing history. The copied price protects each member's deal, and plan immutability protects the catalogue, so we keep both.

  • Enforced in the database. A trigger on plans rejects updates to price, duration_days, pause_days_allowed, max_seats and family. name (typo fixes) and is_active can still change. RLS can't do this, because it checks whether a row can be updated, not which columns change.
  • One action, one transaction. "Change price" on the plans screen calls replace_plan(old_id, new terms). It inserts the new row with replaces_plan_id = old_id and sets the old one is_active = false together, so two versions are never on sale at once.
  • Straight-line history. A unique index on replaces_plan_id means a plan can be replaced only once.
  • Deleting. A plan that has been sold can't be deleted, because memberships reference it and the foreign key isn't set to cascade. An unsold plan created by mistake can still be deleted.
  • Renewals. "Renew same plan" follows the chain to the plan currently on sale. A member who bought at the old price renews at the current one, and any loyalty pricing goes in as a discount.
D4 Agreed 3 Oct

Plans are never edited. A price change creates a new plan with replaces_plan_id pointing at the old one, enforced by a trigger and done through replace_plan().

Price and discount

price is copied from the plan as is and can't be edited in the form. A different price is entered as a discount with a reason (e.g. "Grand opening", "Referral from Arjun"). amount_due = price − discount_amount, and a check keeps the discount between 0 and the price. This way price always means "list price on the day it was sold", every difference has a stated reason, and total discount given can be reported.

D2 Agreed 3 Oct

Copy price, duration_days and pause_days_allowed onto each membership. Keep plan_id for provenance only. Price changes go through the discount.

Status lifecycle

Status is never stored. It's computed from dates, pauses and cancellation by one view (see 09). Payment status is a separate field shown next to it.

Couple Pass

  • One membership, two membership_users rows. max_seats = 2 caps it.
  • Payments attach to the membership. paid_by records whichever partner paid each instalment.
  • Pauses attach to the membership, so both partners pause together. That's how the schema works today. See Q6.
Q3 Open question

Plan changes mid-way, e.g. Monthly → Annual after two weeks. Proposal for v1: no "upgrade" button. Cancel the old membership and sell the new one with a discount for the unused value, with the reason written down. Is that acceptable at the desk?

Paid = sum of payments where status = 'paid'. Pending = amount due − paid. Both come from the summary view, never from a stored column.

Mistakes and refunds

  • Wrong entry: payments are never edited or deleted. The admin voids one with a reason and enters it again. Proposal: add 'void' to the status check, plus void_reason.
  • Refund: status = 'refunded' takes the whole payment out of "paid". Partial refunds don't fit today because amount > 0. See Q4.

Reconciliation

reconciled_at and the payments_unreconciled_idx index exist for a second check. Someone (the owner?) ticks off UPI and card entries against the bank statement, and cash against the day's drawer count. Whoever enters a payment wouldn't be the one who reconciles it.

Q4 Open questions on money
  • Can a membership start with ₹0 paid? Is there a minimum first instalment, or a "pay by" date after which it shows as overdue?
  • Do partial refunds happen? If they do, a refund should be its own row (kind = 'refund') rather than a status flip.
  • Is MaxFit GST-registered? If so, receipts need GSTIN, HSN/SAC 999723 and an 18% tax split, which changes what a receipt row stores.
  • Do we want the reconciliation step, and who does it?
  • Should a receipt go to the member on WhatsApp? That needs an approved utility template.

07Pausing a membership

The member calls, the admin pauses it in the CRM. Only memberships with pause_days_allowed > 0, copied from the plan at sale: 15 days on yearly plans, 7 on six-month, none on monthly or quarterly (per the seed).

Rules

  • Dates are inclusive. Days = paused_to − paused_from + 1.
  • The pause has to start today or later, and within the membership's start_date and end_date.
  • Days used across all pauses + this one ≤ the membership's pause_days_allowed, not the plan's. This needs the allowance trigger back (D1).
  • No overlap with another pause. The existing pause_days_no_overlap constraint already enforces this.
  • Resume early: paused_to becomes yesterday and resumed_early_on today. Unused days go back to the balance.
  • Cancel a future pause: delete the row. Changing the dates of a future pause = cancel + new pause.

Edge case: queued renewal

Priya renews early. The new membership starts the day after the current one ends. Then she pauses the current one, and its end now runs into the renewal. Proposal: the pause function shifts every upcoming membership for those seats by the same number of days, in the same transaction.

Q5 Open questions on pausing
  • Can the admin backdate a pause, e.g. a member who forgot to call before travelling? If so, how many days back?
  • Minimum pause length, e.g. at least 3 days? Without one, a member can spread 15 single days across the year.
  • Can members pause themselves from the portal later? The old request_pause allowed it.
Q6 Open question

Couple Pass: should one partner be able to pause alone? Today a pause belongs to the membership, so both pause together. Pausing one person would mean moving pauses onto seats (membership_users), which changes how the end date is computed.

08What the admin sees

The screens these flows need. They're here so the architecture has a home in the UI. Exact layouts come later.

Members

Search by name or the last 4 digits of a phone number. Each row shows photo, name, status pill and dues. Filters: Active, Paused, Expiring, Expired, Has dues.

Member page

Header with photo, name, phone and a verified chip. A current membership card showing status, days left, pause days left, and paid/pending. Actions: Record payment, Pause, Renew. History of memberships, payments and pauses.

Dues

Every membership with pending > 0, oldest first, with a WhatsApp link to remind the member.

Expiring

end_date in the next 7 days with no renewal queued. This is the list the Trigger.dev reminder job will also use.

Dashboard

Today's numbers from the summary view: active, paused today, starting today, expiring this week, collected today by method, total pending.

Leads

As built, plus "Convert to member" in the drawer, which opens the Add member form pre-filled.

10Also to discuss

You asked what else belongs in the architecture. These are the topics I'd add, roughly in order of how soon the desk will hit them.

Check-ins / attendance

The photo is there to know who's coming in. Do we log visits, and how: the admin taps a member, or members scan a QR at the door? A check-in during a pause or after expiry should warn the desk.

Renewal reminders

The Trigger.dev job is a placeholder. It reads end_date directly, and needs an approved WhatsApp template and a send log, so nobody gets messaged twice.

Cancellations & refunds

Who can cancel, whether money goes back, and how it shows on the books.

Staff roles

Claims today: admin, plans_admin, claims_admin. Should a front-desk role be blocked from discounts above some amount, voiding payments or cancelling?

Audit trail

created_by and marked_by cover creation. Edits to profiles, voids and cancellations need an activity_log if we want "who changed this?"

Member portal

What members can see once they log in: their membership, dues, receipts, pause balance, and maybe self-pause.

Reports

Collected per day by method (to match the cash drawer), monthly revenue, total pending, new vs renewals, lead conversion.

Existing members

Are there pre-opening sales on paper or in a spreadsheet? A one-time import has to set start dates, payments and verification honestly.

Other products

payments.membership_id is nullable. Is that for personal training, supplements or day passes? If yes, they need their own model.

Privacy

Photos, phone numbers and dates of birth are personal data under India's DPDP Act. Decide who can see what, how long we keep it, and what happens when a member asks to be removed.
