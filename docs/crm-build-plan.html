MaxFit CRM, built in small pieces

The architecture turned into tickets small enough that each one is a single PR into dev: easy to test, easy to review, merged in order. Database first, then shared code, then the screens.

Updated 6 Oct 2026Design docs/crm-architecture.html (D1–D16)

How we work

The same loop for every ticket.

  1. One ticket, one branch, one PR. Code tickets branch off dev and open a PR into dev. Migration tickets open their PR into main. Merge, then start the next ticket from the updated branch.
  2. Every PR says how to test it. The "Test" line on each ticket below goes into the PR description. pnpm build and pnpm lint pass before review.
  3. Migrations are new files only. One per database ticket, never an edit to one already applied. Merging a migration PR into main runs the Apply Supabase migrations workflow, which applies it to the production database straight away.
  4. Test locally first. supabase db reset on the local stack applies every migration and the seed. The migration PRs were all checked this way.
  5. Order matters, and the "Needs" line says what. Phases run in order. Inside a phase, a ticket can start once everything it needs has merged.
Testing on prod

You're testing against the live database, so test rows stay there. Leads and payments are never deleted by design. Use one clearly named test member (e.g. "Test · Victor") on your own phone for every flow, and void its payments when you're done.
