MaxFit CRM, built in small pieces

The architecture turned into tickets small enough that each one is a single PR into dev: easy to test, easy to review, merged in order. Database first, then shared code, then the screens.

Updated 4 Oct 2026Design docs/crm-architecture.html (D1–D16)

How we work

The same loop for every ticket.

  1. One ticket, one branch, one PR. Branch off dev as mf-07-membership-terms, open a PR into dev, merge, then start the next ticket from the updated dev.
  2. Every PR says how to test it. The "Test" line on each ticket below goes into the PR description. pnpm build and pnpm lint pass before review.
  3. Migrations are new files only. One per database ticket, never an edit to one already applied. After merging, run pnpm db:push from apps/backend so prod has it before code that needs it.
  4. Order matters, and the "Needs" line says what. Phases run in order. Inside a phase, a ticket can start once everything it needs has merged.
Testing on prod

You're testing against the live database, so test rows stay there. Leads and payments are never deleted by design. Use one clearly named test member (e.g. "Test · Victor") on your own phone for every flow, and void its payments when you're done. Run MF-01 before any migration touches prod.
